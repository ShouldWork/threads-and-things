# Review fixes

These changes are local to `codex/review-fixes`. They have not been committed, pushed, or deployed. No production records were changed during this work.

## Findings, changes, and reasons

| Finding | Change | Why |
| --- | --- | --- |
| Private records and errors survived account changes. | `App` mounts the shop by user identity. `useData` clears data, readiness, and errors, unsubscribes old listeners, and ignores late callbacks from previous accounts, shops, and datasets. | Prevents one account from seeing another account's previous screen or private records. |
| Replacement imports deleted live documents before saving replacements. | Imports validate first, read the current server dataset, stage a complete new dataset in batches, then activate it with one transaction that checks the shop revision. Originals are retained. | Upload failures and concurrent edits leave the active dataset intact; collections and imported settings become visible together. |
| Sales and inventory were saved separately; retries could create duplicates; edits/deletions left inventory sold. | Each form keeps one ID through retries and blocks overlapping submits. Sale creation, edits, SKU changes, and deletions update every affected inventory record in one batch, saving its previous status/outcome for restoration. Rules protect linked inventory against competing sales and inconsistent direct edits. | Prevents partial sale saves, duplicate retry records, and stale sold status. |
| Recent dashboard totals ended at the latest sale and filtered costs inconsistently. | Seven/thirty-day windows end today using local dates. Sales, expenses, mileage, and hours use the same inclusive bounds and exclude future records. Profit/hour includes expenses and mileage; fee totals include selling fees. | Quiet periods now show actual recent activity, and costs/hours correspond to the displayed sales. |
| Dependencies included known vulnerabilities, including the spreadsheet reader. | Updated Firebase, Vite, Vitest, build tooling, and SheetJS; refreshed the lockfile. SheetJS comes from its maintained official distribution. Overrode the vulnerable transitive gRPC version. | Removes the vulnerabilities reported by npm audit at verification time. |
| Offline submissions waited indefinitely for backend acknowledgement; reopening offline lacked an app shell. | Forms resolve after Firestore accepts the local batch, show a queued message, and display pending/cache status plus later sync failures. A production service worker caches the app shell, pages, and assets. Imports require a connection and synced pending writes. | Offline record entry can finish promptly; a previously cached app can reload without a connection. |
| Import deduplication used mutable, truncated sale details and missed duplicates within one upload. | Prefer native transaction/product IDs, retain original identities and confirmed aliases, and review uncertain matches. Update matching source-owned financial fields instead of appending another sale. Identical rows without IDs require review; explicit duplicate consolidation handles existing duplicates. | Reimporting an edited sale no longer creates another copy; different SKUs and description endings remain distinct. |
| Tracker detection depended on the Expenses tab; malformed files could clear collections silently. | Recognize all supported tracker tabs, reject missing headers, validate parsed records, reject malformed numbers, limit files to 20 MB, and require an explicit preview confirmation showing new, updated, unchanged and uncertain rows. | Supports partial trackers and makes updates intentional and reviewable. |
| Firestore rules did not constrain record fields/types or writer roles. | Added verified-email membership checks, owner/editor write roles, collection/field whitelists, numeric/date-format/link bounds, revision checks, and active-dataset write checks. Existing undated inventory can still be linked to a sale. | Invalid and stale-client writes are rejected at the database boundary; read-only members cannot mutate records. |
| Forms accepted blank required dates and negative values; several logs could not be edited. | Shared validation, required dates, nonnegative finite values, positive expense/time/mileage entries, duplicate inventory SKU checks, busy/error handling, and editable expense/mileage/time/issue lists in More. Sale forms expose buyer, selling fees, and fee refunds. | Records can be corrected through the UI and invalid values fail before saving. |
| Sales and listings were silently capped. | Added incremental pagination with remaining-record counts and Show more. | Every loaded record can be reached. |
| Production workflows skipped tests/rules deployment; previews used production Firebase. | Both workflows run unit/build, dependency audit, rule emulator, and browser checks. Production deploys Firestore and Hosting together. PR previews use visibly labelled in-memory demo data; fork PRs validate without deployment secrets. | Failed validation blocks deployment, and preview edits cannot change production shop records. |
| The initial JavaScript bundle included every page, Firestore, and spreadsheet parsing. | Lazy-load the signed-in shop, pages, and spreadsheet parser. | Critical initial JS is about 253 KB / 80 KB gzip versus about 1.11 MB / 320 KB gzip before the changes. Firebase and parsing remain substantial deferred chunks; the service worker downloads the complete offline cache in the background. |
| Additional UI defects found during implementation. | Missing Firebase configuration shows a setup message; labels explicitly reference their controls; dialogs trap/restore keyboard focus; imported select values remain visible; negative chart values render below zero; exact Active status matching excludes Inactive; listing ages advance through today; on-hand inventory excludes disposed items. | Avoids startup crashes, misleading displays, and common keyboard/form failures. |

## Verification

The follow-up import design now preserves IDs, source-column presence, protected field edits, inventory notes/costs, and records absent from a file. Native-ID exports refresh financial values; cross-format/legacy matches require review and are remembered. More includes possible duplicate-sale consolidation, immutable operation history, guarded undo, full JSON backup/restore, clear imported sales, and reset. Clear/reset/restore controls require owner membership and typed in-app confirmation. No existing production duplicates or data were deleted during implementation; those require the user's in-app review after deployment. Detailed behavior is in [IMPORT_WORKFLOW.md](IMPORT_WORKFLOW.md).

- Unit/component/hook suite: **78 passing tests**. Includes account/shop isolation, staged-import failure/concurrency, offline writes, stable IDs, financial updates, source masks, protected edits, duplicate review, inventory reconciliation, backup round trips, recovery operations, and dashboard boundaries.
- Local Firestore emulator: **15 passing tests**. Covers access control, roles, field/import-metadata validation, revisions, staging/activation, retired datasets, batch rollback, competing linked sales, legacy dates, immutable transaction-paired history, read-only published recovery snapshots, and owner-only recovery actions.
- Chromium browser suite: **10 passing tests**. Covers navigation, log CRUD, pagination, labels/validation/focus, offline reload, repeat CSV financial updates, remembered uncertain matches, note/cost preservation, reset/undo/backup restore, imported versus manual sales, duplicate consolidation, and preserving app settings.
- TypeScript and production build pass; the isolated preview build passes.
- `npm audit --audit-level=moderate`: **0 reported vulnerabilities** at verification time.

The browser CRUD checks use the in-memory demo, and the offline reload check covers the production app shell. Hook tests simulate offline write acknowledgement; rule tests use the real local emulator. Live Google authentication, real multi-device/offline synchronization, GitHub Actions execution, and production deployment were not exercised.

## Deployment and operational notes

1. Keep application and rule changes together. New writes increment `shops/{shop}/revision`; the new rules require this. Older cached application versions cannot write under these rules. Close old tabs and reopen the updated app after rollout.
2. Existing `shops/{shop}/{collection}` records remain readable. The first import creates `shops/{shop}/datasets/{version}/{collection}` and sets the shop's `dataVersion`. Subsequent writes target that active version.
3. Previous and failed staged datasets are retained deliberately and consume storage. Each operation publishes a complete dataset copy. Undo restores a fresh copy and is blocked after later changes. Full JSON backup/restore is available in More; restoring a backup explicitly replaces all current records/settings while retaining the pre-restore snapshot. Cleanup requires a separate reviewed administrative task.
4. The deployment service account must have permission to deploy Firestore rules/indexes as well as Hosting. The existing GitHub secret is referenced, but its IAM permissions have not been checked here. Node 22.12+ (CI uses 24) and Java 21 are required for the new tooling/emulator.
5. Identical sales without native transaction IDs cannot be distinguished reliably. The import preview explains this and shows the duplicate count. Offline data remains cached in the browser after sign-out; use a trusted device. First-time sign-in and previously uncached records require a connection.
6. Client validation checks actual calendar dates; database rules check date format and field bounds. Existing malformed data fails with a readable loading error rather than producing broken totals, and may need administrative correction. A remaining build warning concerns the deferred Firebase shop chunk exceeding 500 KB.
